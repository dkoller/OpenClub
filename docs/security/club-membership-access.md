# Installation-local member role lookup

**Current implementation:** `org.openclub.api.members.MemberAccess`. The former `ClubMembershipAccess(personId, clubId)` multi-tenant API is retired in the single-club reset.

`MemberAccess.authorizedClubId(accountId, permission)` now performs a single database-side, installation-local club+membership check. `VIEW_CLUB` permits linked ADMIN and MEMBER roles; interim `MANAGE_MEMBERS` permits only ADMIN. A null result means denied. Only server code selects the permission and the account UUID must come from a verified session. Existing `GET /api/v1/club` uses this check, returning 401 for missing authentication and 403 for authenticated accounts without an authorized local member. These are **interim** checks until #76 defines configurable capabilities and #13 approves member mutations; no member-write HTTP route is enabled.

`MemberAccess.roleFor(accountId)` returns `ADMIN`, `MEMBER`, or `null` by looking up one member in this installation's sole club. No role is granted just by authenticating with OIDC. The account ID must come from a verified server session, never a user-supplied member or account identifier.

**Security boundary:** The lookup is a server-side authorization building block, not an automatic Ktor middleware. Any future state-changing HTTP route must separately enforce trusted session, approved permission, CSRF and Origin before touching private data. `GET /api/v1/club` now invokes the common guard. PostgreSQL `MemberAccessTest` covers authorized admin/member and an outsider. No cross-club lookup or switcher is supported.

**Privacy/release:** See [single-club architecture](../decisions/0005-single-club-installation.md) and [R03](https://github.com/dkoller/OpenClub/issues/12). Tests use synthetic identities only.

## Internal member directory foundation (R09/#18; not an HTTP API)

`MemberDirectory.search(accountId, query, limit, after)` is a PostgreSQL-only query for a trusted installation-local session account ID. It checks both the acting account's linked member **and an explicit club-wide `VIEW_MEMBER_DIRECTORY` grant in the same SQL statement** as the read. No caller-supplied role, club ID, or tenant selector exists; an unlinked account or an account without the directory grant gets an empty result. Only local UUID, first name and last name are selected; birth dates, contact details, gender and login identities are never loaded into the summary. Queries use bound parameters and literal substring matching, not wildcard matching; names sort deterministically by last name, first name, then UUID. Limit is 1–50, default 20; the next-page key is an **internal typed value**, never a public, unsigned cursor.

**Exposure gate:** No Ktor route is registered for this query. R03/#12 must approve directory visibility (particularly children), R06/#15 and #76 must approve fine-grained capabilities, and R04/#13 must finalize an authenticated, tamper-resistant opaque public cursor before a member-directory HTTP endpoint is enabled. Do not mistake this internal query or synthetic SQL test for approval to handle real member data.

## Explicit club-wide capability checks — R01/#76 increment

Flyway `V2__club_capability_grants.sql` introduces **installation-local**, explicitly stored member grants for `VIEW_MEMBER_DIRECTORY`, `EDIT_MEMBERS` and `MANAGE_PERMISSIONS`. There are no tenant IDs or global accounts. Each (member, capability) combination is unique, and deleting a member removes its grants. Only the restricted first-club bootstrap seeds the first ADMIN member with `MANAGE_PERMISSIONS` inside the same transaction; no other ADMIN automatically inherits grants. **Upgrades with a pre-existing ADMIN intentionally do not backfill grants**: a separately reviewed operator-controlled initialization procedure is required before adding a grant UI.

`ClubCapabilityAccess.has(verifiedSessionAccountId, capability)` checks the current database state on every call; missing, revoked or unlinked member grants deny immediately. Managing permissions requires **both** an explicit `MANAGE_PERMISSIONS` grant and an `ADMIN` role. Being an ADMIN alone, managing members, or holding a directory grant does not confer delegation powers. This is a read-only security building block: there is no grant/revoke HTTP endpoint and no permission UI. Direct SQL fixture writes in PostgreSQL integration tests are **not a delegable application interface**.

**Deliberate limitations:** team-specific grants cannot be modeled safely until teams/member assignments (#75) exist, so no dangling `team_id` field or imaginary team authorization was added. Grant/revoke transactions must prevent self-escalation, over-delegation, loss of the final permission manager and concurrent races before any public API is enabled. Existing `VIEW_CLUB` and interim `MANAGE_MEMBERS` routes retain their earlier behavior; new capabilities do **not** implicitly authorize member HTTP APIs or sensitive contact visibility. R03/#12 privacy, R04/#13 contract review, R06/#15 route enforcement, and #76 delegation testing remain open.

## Installation-local teams and assignments (#75)

Flyway V3 adds `teams` and `member_team_assignments`, using local member/team UUIDs and a unique (team, member) pair. Team names are unique ignoring case; deleting a team/member cascades its assignments. Members may belong to multiple teams without copying their personal data. V3 also extends the fixed club-wide grants with `VIEW_TEAMS` and `MANAGE_TEAMS` **without automatically granting either capability**.

`TeamAssignments` is **internal-only**, not a Ktor route. Its trusted account ID must come from a verified session. Creation, rename, deletion, assignment and unassignment each check an explicit `MANAGE_TEAMS` grant inside the same SQL statement performing the mutation; list requires `VIEW_TEAMS` or `MANAGE_TEAMS`. A valid login, ADMIN role alone, ordinary team membership and permission to edit members cannot manage teams. Duplicate assignments return false even under competing insertions, and deleting a team removes its assignments.

**Still blocked:** No club/team-scoped delegated grants, no team HTTP API or multilingual UI. Team-scoped grants must bind to actual team IDs, enforce allowed actions on targets, and support revocation/last-manager safeguards under #76. R03/#12 privacy review and final R04/#13 contracts remain mandatory before exposing team-member identities. Internal SQL operations must be called on `DatabaseRuntime.onDatabaseThread`, never the Ktor event loop.

## Team-scoped capability enforcement (V4; #76 increment)

V4 adds `team_capability_grants(team_id, member_id, capability)` with foreign keys to actual local teams and members, a unique team/member/capability tuple and cascading deletion. Only `VIEW_TEAMS` and `MANAGE_TEAMS` are valid at team scope; `EDIT_MEMBERS` and `MANAGE_PERMISSIONS` **cannot** be granted at team scope. No grants are created automatically.

`ClubCapabilityAccess.hasForTeam(verifiedSessionAccountId, teamId, capability)` checks either an explicit club-wide grant or an explicit grant **for that exact team** in the current database. A team `MANAGE_TEAMS` grant implies team visibility, not club-wide control. Internal `TeamAssignments.list` returns only teams for which the actor has scoped/team-wide read/manage authority. Assignment and unassignment check club-wide or matching team `MANAGE_TEAMS` **inside the same SQL statement**. Team creation, renaming and deletion still require **club-wide** `MANAGE_TEAMS`. Revoking or unlinking a grant denies subsequent operations; deleting a team/member removes grants automatically.

**Not an API or delegation mechanism:** These are internal backend operations with synthetic tests, not permission-edit routes. Database fixture writes are privileged test setup, never client-accessible. Safe grant/revoke authorization, prevention of self-escalation/over-delegation, last-authorized-manager protection, concurrent grant changes, member field visibility, privacy approval and frontend UI remain open under #76/#12/#13. No member/team HTTP route has been introduced. Blocking SQL must run through the bounded database dispatcher.

## Serialized internal grant mutations (#76)

`CapabilityGrants` provides **internal-only** `grant` and `revoke` operations with a verified session account ID and explicit `CLUB` or `TEAM` scope. All operations run in a PostgreSQL transaction under the same installation-wide advisory lock; the manager's ADMIN role plus explicit club-wide `MANAGE_PERMISSIONS` grant are rechecked inside that transaction. Unknown recipients and nonexistent teams fail closed. Team-scoped grants may include only `VIEW_TEAMS` and `MANAGE_TEAMS`, never member-edit or permission-management rights. Duplicate grants and revokes are idempotent.

The actor cannot modify their **own grants**, preventing self-escalation and accidental self-lockout. A `MANAGE_PERMISSIONS` grant can be issued only to an ADMIN member whose account has a verified OIDC identity binding. Last-manager checks count only administrators with such a binding, not accountless or unverifiable administrators. Revocation rejects removal of the last eligible ADMIN permission-manager; serialized grant mutations avoid competing revocations. Other role changes are outside this service: **R10/#19 must use the same transaction lock and last-manager invariant** before role demotion, deletion or unlinking can be exposed. This API does not protect against a privileged operator directly manipulating SQL.

**Not web-exposed:** No grant/revoke HTTP route, public administrator interface, or audit trail is introduced. Caller-supplied actor IDs must never reach this internal interface; production HTTP mutations also require validated session, Origin, CSRF, error masking and audit policy. R03/#12 privacy, R04/#13 contract acceptance, and independent security review remain pending.

## Internal protected role changes (#19)

`MemberRoles.change(verifiedSessionAccountId, targetMemberId, role)` allows only an ADMIN holding an explicit club-wide `MANAGE_PERMISSIONS` grant to change **another** member's `ADMIN`/`MEMBER` role. Self-change, unknown actor/target, unlinked account, and absent permission are denied. The service holds the **same PostgreSQL transaction advisory lock** as `CapabilityGrants` (#92), so racing role changes and grant revocations cannot remove the final authorized administrator/permission-manager through these service paths. Demotion checks that at least one ADMIN remains and, if the target is an eligible permission manager with a verified OIDC identity binding, that another eligible manager remains. Every role transition also clears the target's `MANAGE_PERMISSIONS` grant in the same transaction, so a demoted user cannot regain delegation authority automatically on later promotion; a separate explicitly authorized grant is required. The role is never inferred from a request.

This is a **backend-only security foundation**. No role-change HTTP endpoint, admin UI or audit ledger exists. Full authorization, exact Origin/CSRF, reviewable API contract, privacy and concurrent unlink/archive/delete guards are still needed before exposing member role management. Direct privileged SQL bypasses these service invariants and must remain operator-restricted.

## Accountless member creation foundation (#18)

`MemberCreation.create(verifiedSessionAccountId, input)` is an **internal-only** jOOQ operation that creates an installation-local member with a generated UUID and **no linked account**. It authorizes the acting account using an explicit, current club-wide `EDIT_MEMBERS` grant **inside the INSERT ... SELECT**; unlinked or ungranted accounts insert nothing. No club ID, OIDC account, identity binding, role or capability can be supplied through the input. Duplicate names are permitted because they are not a trustworthy identity key.

Names are trimmed and length-limited; date of birth is required and cannot be future-dated; optional contact/gender strings are trimmed. The PostgreSQL trigger remains authoritative for configured adult email **and** phone, and conditional player-gender rules. Invalid records are rejected rather than silently dropping required fields. Database errors are internal and must be converted to nondisclosing API responses **only after** an approved HTTP interface is designed.

**Security/privacy gates:** No Ktor route, browser form submission or new authority has been introduced. Before exposing any member-creation endpoint, approve R03/#12 legal/field policy and the R04/#13 contract, verify trusted session, exact Origin, CSRF, field-level authorization and safe audit/error behavior. Continue using synthetic tests only. Execute blocking JDBC work via `DatabaseRuntime.onDatabaseThread`.

## Protected member details update (#18)

`MemberDetailsUpdate.update(verifiedSessionAccountId, memberId, input)` is an **internal-only** database operation. It changes only first/last name, birth date, adult contact, player gender and player status. It deliberately cannot change local member ID, OIDC account link, ADMIN/MEMBER role or capability grants: those are separate privileged operations with their own last-manager and identity safeguards. The acting account must hold a current explicit `EDIT_MEMBERS` club-wide grant, checked **inside the same UPDATE**. Unknown IDs, unlinked accounts and revoked/ungranted actors do not update rows.

Names, dates and contact lengths are validated before persistence; the PostgreSQL trigger remains authoritative for adult email-plus-phone and configured player-gender rules. Callers must not treat a database validation exception as a safe public response or echo private input in logs. This service has **no HTTP route**, browser submission, or field-read API, and does not authorize real data: R03 privacy, R04 contract, audit, session/Origin/CSRF and field-level visibility must all be reviewed before exposure.
