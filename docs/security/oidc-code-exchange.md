# R05 / C4b — Internal authorization-code exchange

**Status:** Internal component only, not an HTTP login or session. [Issue #14](https://github.com/dkoller/OpenClub/issues/14); built on the merged discovery ([#55](https://github.com/dkoller/OpenClub/pull/55)), pre-auth transaction ([#53](https://github.com/dkoller/OpenClub/pull/53)) and token verifier ([#54](https://github.com/dkoller/OpenClub/pull/54)).

`OidcAuthorizationCodeExchange` accepts an authorization code and an **already consumed** `ConsumedOidcLogin` (server-held nonce and PKCE verifier). Nimbus builds the confidential `client_secret_basic` authorization-code grant with exact configured callback URI and PKCE verifier. The Java 21 HTTP client posts to the trusted same-origin token endpoint with no redirects, a 3-second connection timeout, a 5-second full-response deadline and a streaming 16-KiB body limit. Redirects, provider errors, malformed responses, invalid content-type and timeouts fail closed without surfacing token or secret values. Nimbus parsing/verification exceptions are translated into a generic error **without an exception cause** because received JWT claims can appear in Nimbus messages; normal stack-trace logging must not expose those claims.

Nimbus parses the OIDC token response. The *only* returned value is the verified issuer + subject, after signed ID-token and nonce validation by `OidcIdTokenVerifier`. Access/refresh tokens are not persisted, logged or sent to React. A matching issuer + subject is **not** membership authorization; club access and account linking still require their separate security gates.

**Important limitations:** No HTTP login/callback route or session exists. The caller must consume the browser-bound five-minute state transaction *before* this operation, avoid any retry of the one-time authorization code, and run synchronous network/database work off Ktor event loops. Keycloak currently advertises browser-local `localhost:8180`; the API container cannot use it internally. Before enabling routes, design and test an issuer-consistent backchannel, choose robust discovery/JWKS refresh and token endpoint outage handling, and implement session/CSRF protection. Never weaken issuer verification.

Loopback HTTP tests use synthetic, signed RS256 tokens and check encoded grant parameters, Basic client authentication, valid identity, provider failures, wrong nonce with a sensitive-marker stack-trace assertion, redirect, malformed responses, and size/time failures (including a stalled chunked body and exactly one POST). No live Keycloak credentials or personal data are used. The API/OpenAPI remains unchanged because no route is exposed. See [security checklist](../contributing/security-review.md).
