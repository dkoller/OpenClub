# R05 / E1 — Verified OIDC identity to person resolution

**Status:** Installation-local verified OIDC account resolution; now used by the R05 implemented login flow. Not local membership authorization. Parent [R05/#14](https://github.com/dkoller/OpenClub/issues/14). No OpenAPI change: no route is added.

`VerifiedAccounts.resolveOrCreate(identity)` accepts **only a `VerifiedOidcIdentity` issued by the trusted signed-ID-token verification flow**, with an exact match to the configured deployment issuer and a nonempty case-sensitive ASCII OIDC subject (maximum 255 characters). The `VerifiedOidcIdentity` data type itself is not proof of validation: a future Ktor handler must never construct it from request headers, URL parameters or JSON. Call the resolver only **after** browser-bound state consumption, confidential code+PKCE exchange and signed ID-token validation.

The existing `account_identities` database uniqueness constraint on `(issuer, subject)` is the sole account binding. Repeated logins resolve to the same account. First login creates a minimal new `accounts` record with placeholder display name `Unlinked OpenClub account`, **no membership or role**, plus the verified identity. It **does not** adopt an existing member by matching email, name, display name or other unverified claims. Joining an existing member record requires a separate, explicitly verified invitation/account-linking workflow (see [ADR-0002](../decisions/0002-identity-and-membership-model.md), [#20](https://github.com/dkoller/OpenClub/issues/20)).

Creation runs in a jOOQ-managed PostgreSQL transaction. A concurrent login that loses the unique identity binding deletes its unused candidate account *inside* the transaction and resolves the committed winner; errors fail closed. The resolver uses only jOOQ, does not create a session, does not infer membership and does not return tokens. It performs blocking JDBC work, so future Ktor routes must execute it on a bounded I/O dispatcher. Do not log identity claims, tokens or SQL bind values containing subject identifiers.

PostgreSQL integration tests cover repeated resolution, case-sensitive distinct subjects, issuer pinning, malformed subjects, refusal to adopt an existing club **ADMIN** with the same display name, no inherited membership, and **deterministic** simultaneous first logins yielding one account/binding. A test-only jOOQ execution listener blocks each transaction immediately after its candidate-person INSERT, until both inserts have completed. The test explicitly asserts two competing identity INSERT attempts and exactly one losing candidate DELETE, ensuring the conflict/cleanup branch actually executes. The integration suite requires `DB_URL`, `DB_USER`, `DB_PASSWORD` (set in CI). No live personal data is used.

**Remaining before login:** live API-scoped DB pool and dispatcher, browser-bound transaction cookie, protected login/callback handling, secure HttpOnly session cookie, exact-origin CSRF controls, JWKS refresh/rotation, rate limits, and end-to-end Keycloak tests. Authentication is not authorization: R06/#15 and first-admin #16 precede public member administration.


**Single-club reset (2026-11-15):** `VerifiedAccounts` writes only local `accounts` and `account_identities` in the sole installation database. It never creates, adopts or synchronizes a member record, even if an account email matches a member. No global person profile remains. See [ADR-0005](../decisions/0005-single-club-installation.md).
