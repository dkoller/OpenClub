# R05 / D1 — PostgreSQL opaque session store

**Status (2026-11-14):** Opt-in login/callback and session routes now exist; default authentication remains disabled. No member routes. See [session API](session-api.md).

Fresh Flyway `V1__single_club.sql` adds a separate authenticated-session table. The browser's 256-bit random session handle is **never persisted as plaintext**: only its SHA-256 digest is the primary key. Each session references an existing `accounts.id` and has a distinct 256-bit CSRF token stored server-side, creation/last-use timestamps, a **30-minute idle expiry** and an **unextendable 12-hour absolute expiry**, determined by PostgreSQL's clock.

`AuthSessions.create(accountId)` accepts a account ID **only from trusted, already verified issuer+subject resolution**, not from an HTTP header, query or arbitrary member record. `find(handle)` returns the authenticated account and CSRF token; `findForMutation(handle, csrfToken)` additionally requires matching CSRF and does **not** refresh idle expiry if it fails. The eventual route must ALSO validate exact same-origin `Origin` and appropriate JSON content type; CSRF alone is not sufficient. `rotate(handle)` atomically replaces both handle and CSRF token, invalidates the old handle and preserves hard expiry. `revoke(handle)`, `revokeAllForAccount(accountId)` and `pruneExpired()` support logout, lifecycle revocation and cleanup. The implemented R05 runtime starts a bounded cleanup job when OIDC is configured. Account deletion cascades to sessions.

**Do not return `csrfToken` in any response except authenticated, same-origin `GET /api/v1/auth/me`,** and never log session cookies, CSRF tokens, bind values or secrets. CSRF token is stored in plaintext inside the trusted session database so /auth/me can return it; restrict the database role, backups and diagnostics. Session handle is never accessible to JavaScript: use `__Host-openclub_session` with Secure/HttpOnly/SameSite=Lax/Path=/ in HTTPS production and a separate explicit local-HTTP dev name. Cookie configuration, route-level origin enforcement, identity mapping and periodic cleanup are follow-up changes.

All jOOQ/JDBC calls are synchronous. Future Ktor handlers **must run them on a bounded I/O dispatcher**, not the event loop; maintain a live scoped connection pool rather than using the temporary migration pool. Fail database errors closed. Session identity does **not** grant club access: R06/#15 must check the authenticated account's membership/role for the sole installation club and each authorized team.

PostgreSQL integration tests (with `DB_URL`, `DB_USER`, `DB_PASSWORD`, as in CI) cover hashes, forged/missing handles, CSRF rejection preserving **both** `last_used_at` and `idle_expires_at`, valid reads/mutations extending a shortened idle deadline to approximately 30 minutes, access and rotation clamping the idle deadline to a near-term absolute expiry, single-use rotation, hard-expiry preservation, pruning, revocation, FK deletion and DB failure. No OpenAPI changes because no routes are added. See [BFF design](oidc-bff-design.md) and [security checklist](../contributing/security-review.md).


**Architecture update (2026-11-15):** sessions now link to local `accounts.id`; they contain no member profile data or club switching. See [ADR-0005](../decisions/0005-single-club-installation.md). Real member data remains subject to privacy/release gates.

## Revoked OIDC identity invalidates active session reads (PR #229, synthetic M1)

The PostgreSQL session read, CSRF-bound mutation lookup and rotation now check for a **current verified account-identity association in the same SQL statement** that refreshes idle expiry or rotates the session. Removing the identity makes already-issued session cookies unusable for `/api/v1/auth/me` and subsequent authenticated operations, even if `auth_sessions` still contains the hashed handle. Rejected calls do not extend the idle deadline or rotate the handle. The explicit CSRF-checked logout path remains available to clear the stale handle. Synthetic PostgreSQL tests verify these properties. This complements rather than replaces capability checks, and does not automatically delete historical session rows or establish M2 production revocation procedures.

## Revoked-cookie Ktor acceptance (PR #230, synthetic M1)

A PostgreSQL-backed Ktor integration test now calls the actual `GET /api/v1/auth/me` route with an issued opaque session cookie, removes the verified account-identity row, and verifies that the **same cookie** receives 401 with `Cache-Control: no-store`. The CSRF- and Origin-protected logout remains available to clear the old session cookie and delete the stored session. This closes the HTTP-level regression gap left by the service-only SQL tests from PR #229. It uses a fictional local account, no external identity provider or real personal data; full external TLS/OIDC deployment and M2 operational review remain open.
