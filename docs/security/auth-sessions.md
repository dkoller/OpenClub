# R05 / D1 — PostgreSQL opaque session store

**Status (2026-11-14):** Opt-in login/callback and session routes now exist; default authentication remains disabled. No member routes. See [session API](session-api.md).

Flyway `V4__auth_sessions.sql` adds a separate authenticated-session table. The browser's 256-bit random session handle is **never persisted as plaintext**: only its SHA-256 digest is the primary key. Each session references an existing `persons.id` and has a distinct 256-bit CSRF token stored server-side, creation/last-use timestamps, a **30-minute idle expiry** and an **unextendable 12-hour absolute expiry**, determined by PostgreSQL's clock.

`AuthSessions.create(personId)` accepts a person ID **only from trusted, already verified issuer+subject resolution**, not from an HTTP header, query or arbitrary member record. `find(handle)` returns the authenticated person and CSRF token; `findForMutation(handle, csrfToken)` additionally requires matching CSRF and does **not** refresh idle expiry if it fails. The eventual route must ALSO validate exact same-origin `Origin` and appropriate JSON content type; CSRF alone is not sufficient. `rotate(handle)` atomically replaces both handle and CSRF token, invalidates the old handle and preserves hard expiry. `revoke(handle)`, `revokeAllForPerson(personId)` and `pruneExpired()` support logout, lifecycle revocation and cleanup. **No scheduled cleanup job is yet running.** Person deletion cascades to sessions.

**Do not return `csrfToken` in any response except authenticated, same-origin `GET /api/v1/auth/me`,** and never log session cookies, CSRF tokens, bind values or secrets. CSRF token is stored in plaintext inside the trusted session database so /auth/me can return it; restrict the database role, backups and diagnostics. Session handle is never accessible to JavaScript: use `__Host-openclub_session` with Secure/HttpOnly/SameSite=Lax/Path=/ in HTTPS production and a separate explicit local-HTTP dev name. Cookie configuration, route-level origin enforcement, identity mapping and periodic cleanup are follow-up changes.

All jOOQ/JDBC calls are synchronous. Future Ktor handlers **must run them on a bounded I/O dispatcher**, not the event loop; maintain a live scoped connection pool rather than using the temporary migration pool. Fail database errors closed. Session identity does **not** grant club access: R06/#15 must check the authenticated person's membership/role for each club.

PostgreSQL integration tests (with `DB_URL`, `DB_USER`, `DB_PASSWORD`, as in CI) cover hashes, forged/missing handles, CSRF rejection preserving **both** `last_used_at` and `idle_expires_at`, valid reads/mutations extending a shortened idle deadline to approximately 30 minutes, access and rotation clamping the idle deadline to a near-term absolute expiry, single-use rotation, hard-expiry preservation, pruning, revocation, FK deletion and DB failure. No OpenAPI changes because no routes are added. See [BFF design](oidc-bff-design.md) and [security checklist](../contributing/security-review.md).
